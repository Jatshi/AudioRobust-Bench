# AudioRobust-Bench 2.0：升级说明、原理学习与工程复盘

## 1. 为什么要做这个项目

真实语音系统通常不是在安静录音棚里工作。会议麦克风会有混响，电话链路会丢包，远场语音会被空调噪声覆盖，同一段音频送入 ASR、说话人模型和声音事件模型后还会出现完全不同的退化曲线。只展示一个干净样本的 Demo，无法回答“噪声变大以后系统何时失效、是否仍然过度自信、不同模型能否公平比较”这些部署问题。

AudioRobust-Bench 2.0 的目标不是再训练一个音频模型，而是建立统一、可复现、可追责的可靠性测量层：同一份 corruption manifest 驱动多个任务；每个样本、随机种子和模型版本都写入 manifest；报告同时给出质量、失败率、校准误差和不同强度切片。这样，项目从“若干音频模型的演示”升级为“面向生产验收的评测基础设施”。

## 2. 2.0 新增内容

- 新增真实模型适配器：Faster-Whisper ASR、WavLM 说话人嵌入、AST 声音事件分类。
- 新增公开样本下载器，支持 SHA-256 校验、已下载文件复用和镜像回退。
- 新增统一 GPU smoke 流程，落盘环境、模型、输入哈希、逐强度结果与指标边界。
- 将“准确率”拆成三类不同含义：ASR 是有参考文本的任务质量；说话人是相对干净锚点的一致性；事件分类是相对干净 top-5 的一致性。
- 增加模型不可用、下载失败和依赖冲突的显式失败路径，不再静默回落到假数据。

## 3. 从零手搓时应该怎样拆解

### 3.1 先定义不可变的实验对象

一个 corruption case 至少包含：源音频 ID、扰动类型、强度、随机种子和输出 ID。ID 应由这些字段稳定生成，而不是使用当前时间。这样同一个 case 在两台机器上会得到同一标识，结果才能合并、去重和复查。

### 3.2 再把信号扰动与模型推理解耦

扰动层只接受波形并返回波形；任务适配器只接受一个 case 并返回 score/confidence/error。ASR 不应该知道噪声是怎样生成的，噪声模块也不应该依赖 Whisper。这个边界让同一组 case 可以公平地喂给不同模型，也让单元测试无需下载大模型。

### 3.3 最后统一聚合

对任务分数 `s_i`、置信度 `c_i` 和强度桶 `b_i`，报告至少需要：

- 平均质量：`mean(s_i)`；
- 失败率：推理异常或无有效输出的比例；
- 强度切片：`E[s | b=k]`；
- ECE：先按置信度分桶，再累加 `|accuracy_bin - confidence_bin| * bin_weight`。

ECE 不是准确率。一个模型可能准确率较高，但在噪声下仍然过度自信；这正是可靠性评测要额外揭示的问题。

## 4. 真实 4090 验证结果

运行环境为 RTX 4090、PyTorch 2.9.0+cu128。输入是公开 JFK 音频，SHA-256 为 `59dfb9a4...ba7860e`。真实加载的模型为：

- `Systran/faster-whisper-tiny.en`；
- `microsoft/wavlm-base-plus-sv`；
- `MIT/ast-finetuned-audioset-10-10-0.4593`。

三档 SNR（clean、10 dB、0 dB）结果：ASR 平均字符准确度 0.9398，clean/10/0 dB 分别为 1.0000/0.9639/0.8554；说话人一致性平均 0.8951；事件 top-5 一致性平均 0.4667。完整证据见 `artifacts/smoke/run_manifest.json`。

这些数字只证明 smoke 样本上的退化行为，不能写成“大规模 benchmark 准确率”。说话人和事件结果也不是带人工真值的任务准确率；它们衡量的是相对干净锚点的一致性。

## 5. 本次最重要的坑与解决方式

### Python 与 SciPy 版本

Python 3.10 环境直接安装新的 SciPy 约束失败。解决方式不是盲目升级整个环境，而是根据 Python ABI 固定 `scipy==1.15.3`，然后把环境 freeze 文件一起保存。面试时可说明：依赖版本是实验协议的一部分，不是“能 import 就行”。

### 公共样本下载超时

AutoDL 到 GitHub 原始文件的连接超时，但本地网络可以快速下载。最终方案是本地下载、校验哈希后上传，并修改下载器：若目标文件已存在且哈希正确则直接复用，否则按主 URL 和镜像顺序尝试。这样既节省付费 GPU 时间，也不会使用来源不明的文件。

### 指标名称容易过度声明

最初容易把 WavLM embedding cosine similarity 写成“克隆质量”，把 AST top-5 重合写成“事件准确率”。这两种表述都不成立。最终在 manifest 中增加 `measurement_scope`，把可验证事实和不能声称的边界一起写入产物。

## 6. 面试高频问题

**为什么不用一个总分？** 不同任务的分数含义和量纲不同，总分会隐藏某个任务的危险退化。统一的是实验协议和报告结构，不是强行统一任务语义。

**为什么 clean 作为锚点仍有价值？** 当人工标签昂贵时，一致性可以快速发现噪声敏感性；但它不能替代真值评测，所以报告必须明确 scope。

**怎样扩展到分布式评测？** manifest 按稳定 case ID 分片，各 worker 独立推理并写 append-only 结果，汇总端按 ID 去重。模型权重可由每个 rank 各自加载，或由服务端集中推理；关键是聚合结果不能依赖执行顺序。

**怎样防止 benchmark 被模型“刷分”？** 保留隐藏扰动组合、固定公开协议、报告多强度曲线和校准，并要求提交完整 manifest，而不是只接受一个最优均值。

## 7. 建议亲手复现的练习

1. 新增带通限幅 corruption，并写两个边界测试。
2. 把 SNR 从三档扩展为 20/10/5/0/-5 dB，画质量—强度曲线。
3. 人工制造一个“准确但过度自信”的预测集，手算 ECE 后与代码核对。
4. 增加第二个 ASR 适配器，证明 corruption 层无需修改。
5. 用两个本地进程按 case ID 分片，再验证合并结果与单进程完全一致。

完成这些练习后，你应该能不依赖项目代码，独立解释 manifest、adapter、corruption、slice、ECE 和 claim boundary 的设计原因。
